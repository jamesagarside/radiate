# Design standards

These are the rules for Radiate's web UI. The sources are in `web/` and build into `src/radiate/web` (see [Change the web UI](../deployment.md#change-the-web-ui)). The same UI runs standalone on port 8099, in the Home Assistant sidebar through ingress, and in the online demo. People glance at it many times a day, so it should be calm, quick to read, and say what the heating is doing.

Radiate uses [Web Awesome](https://webawesome.com/) 3 (MIT) as its design system, with Web Awesome's own look: the "awesome" theme, the "bright" palette and the orange brand (`<html class="wa-theme-awesome wa-palette-bright wa-brand-orange">`). Use its components, layout utilities and tokens before writing anything of your own. Radiate's own CSS is layout glue plus the few things Web Awesome has no token for: the temperature scale and a cool blue variant. The one drawing kept from the earlier design is the house model.

Every view is built from Web Awesome components: cards, badges, tags, callouts, buttons, radio groups, switches, progress bars, details, a drawer, a dropdown and toasts. Text inputs, selects and date fields in the forms (Settings, the household setup, Raw data, the week editor) are native elements drawn by Web Awesome's native styles, because they carry `aria-invalid` and `aria-describedby` that a Web Awesome input wouldn't pass to its inner control. Buttons that need their own ARIA (a label naming the room, `aria-expanded`, `aria-pressed`) are native buttons for the same reason, with Web Awesome's `wa-outlined`, `wa-brand` or `wa-plain` classes.

The values on this page are the ones in `web/src/styles/app.css`, `house.css`, `views.css`, `savings.css`, `settings.css`, `data.css` and `guide.css`, and in `web/src/wa.js`. Change the code and this page together.

## Principles

- **Explain the house.** Every room says, in words, why Radiate is doing what it does.
- **Use the system.** Reach for a Web Awesome component, then a layout utility (`wa-stack`, `wa-cluster`, `wa-split`, `wa-grid`), then a `--wa-*` token. Write custom CSS only when none of those does the job, and build it from tokens.
- **Numbers line up.** Readouts (temperatures, counts, times) use tabular figures (`.readout`), so live values don't shift sideways as they change.
- **Motion only where it explains a state change.** A bar moving to a new opening limit tells the reader something. Decoration that people see dozens of times a day becomes friction.
- **Good defaults over options.** Light and dark follow the device. There is no theme picker or layout setting.
- **Update in place.** The House view is drawn with lit-html templates (`render` from `lit`) and the other views create elements once, so a tick changes text and attributes without rebuilding controls, and focus survives.

## Theme and colour

Web Awesome's semantic tokens carry every colour: surfaces (`--wa-color-surface-default`, `-raised`, `-lowered`, `-border`), text (`--wa-color-text-normal`, `-quiet`, `-link`) and the variants `brand`, `neutral`, `success`, `warning` and `danger`, each with `fill`, `border` and `on` tokens at `quiet`, `normal` and `loud`. Use the matching `on` token on a fill (`fill-quiet` with `on-quiet`). Never hard-code a colour, apart from the temperature scale below.

Colour carries meaning, so keep it consistent. Every coloured state also has a text label, so colour is never the only signal.

| Meaning | Variant | Used for |
|---|---|---|
| Heat | `brand` (orange) | Heating, Fire lit, Topping up badges; the Firing chip; burns on the timeline; the selected link in the menu |
| Waiting or needs attention | `warning` | Preheating, Waiting for a burn, Due back, No update badges; Opening valves; alerts, the dry run notice, the stuck-valve note, short-cycling, devices that need attention |
| Comfortable | `success` | Comfortable, Online, Ready |
| Calm, set by Radiate or a person | `radiate-cool` (below) | Heat sink, Away and Held; the Resting chip; hot water on the timeline; the demo banner, the guide note and the away notes |
| Everything else | `neutral` | Idle, Waiting, Home, Out, Bypass and No radiator badges; lock tags |

`danger` isn't used: nothing in Radiate is an error the reader caused.

**Cool.** Web Awesome's variants have no blue, so `app.css` adds one built the way the theme builds `brand`, from the palette's blue: `--radiate-cool-fill-quiet` (blue 95, dark 10), `-fill-normal` (90, dark 20), `-fill-loud` (50), `-border-quiet` (80, dark 30), `-border-normal` (50), `-on-quiet` and `-on-normal` (40, dark 80). The class `radiate-cool` maps them onto `--wa-color-fill-*`, `--wa-color-border-*` and `--wa-color-on-*`, so it works on `<wa-badge>`, `<wa-tag>` and `<wa-callout>` like a variant.

**Temperature scale.** Rooms are coloured by their reading in the house model, the rooms list swatches, today's plan, "Where every room sits" and the 12° to 22° key. `house.js` reads these hex tokens and blends between them, clamping outside 12° and 22°.

| Token | Light | Dark | Temperature |
|---|---|---|---|
| `--t12` | `#3e63dd` | `#3e63dd` | 12° and below |
| `--t15` | `#8ec8f6` | `#2870bd` | 15° |
| `--t17` | `#e2e1de` | `#62605b` | 17°, the neutral middle |
| `--t19` | `#ffc53d` | `#ffc53d` | 19° |
| `--t22` | `#e54d2e` | `#ec6142` | 22° and above |
| `--hm-none` | `#e8e8ec` | `#2e3135` | A room with no reading |
| `--hm-line` | `#c9ccd3` | `#3b3f45` | Floor outlines in the model |

Text on a temperature colour in the model is ink or white, whichever has the higher contrast (`inkOn` in `house.js`). Readings in the model are 17 px bold. Each room's name and reading is also in its accessible name, and in the rooms list.

**Light and dark.** Web Awesome switches scheme with a class, not a media query. A one-line script in each page's `<head>` adds `wa-dark` or `wa-light` from `prefers-color-scheme` before first paint, and `web/src/wa.js` keeps it current when the device setting changes. Write dark-mode rules against `.wa-dark`, never `@media (prefers-color-scheme: dark)`. The house model redraws when the class changes.

## Type

The "awesome" theme sets Quicksand for body and headings. Radiate serves it with the UI from `@fontsource/quicksand` (SIL Open Font License 1.1): Latin and Latin Extended, weights 400, 500, 600 and 700. The theme's own stylesheet imports its fonts from a font CDN; the build strips that import (`noRemoteImports` in `web/vite.config.js`), and a test checks no CSS imports anything.

Use Web Awesome's type utilities and tokens rather than sizes of your own:

| Role | Class or token |
|---|---|
| View heading ("House") | `wa-heading-xl` |
| Card and section headings | `wa-heading-m` (`wa-heading-s` for a person's name) |
| Selected room's name | `wa-heading-l` |
| Room temperature in the details | `.readout .readout-xl` (`--wa-font-size-2xl`, bold) |
| Target and opening limit in the details | `.readout .readout-l` (`--wa-font-size-xl`) |
| Rooms calling on the house now | `--wa-font-size-4xl`, 3xl under 32rem |
| Boiler statistics | `.stat-value`, `--wa-font-size-l` bold |
| Status line, help lines | `--wa-font-size-s`, `--wa-color-text-quiet` |
| Labels and small print | `wa-caption-m`, `wa-caption-s` |

Headings and labels use sentence case. Every number that changes live uses `font-variant-numeric: tabular-nums` (`.readout`).

## Icons

Icons are Font Awesome Free, solid style (icons CC BY 4.0; each SVG keeps its licence comment). `web/src/wa.js` registers Web Awesome's default icon library to load them from `static/icons/<name>.svg`, so nothing comes from the Font Awesome CDN. At build time `web/vite.config.js` copies only the icons the sources name: write icon names out in full, as `<wa-icon name="house">`, `icon: "house"` or a `tile("house", …)` in `house.js`, and the build fails on a name Font Awesome Free doesn't have. Web Awesome's own system icons (chevrons, the stepper's minus and plus) are built into its components.

An icon that carries meaning has a `label`; a decorative one beside its text has none.

## Layout and shape

| Piece | How it is done |
|---|---|
| Page | `<wa-page mobile-breakpoint="920">`: header (brand, outdoor temperature, account menu), subheader (the status line), navigation (the views), main and aside |
| Navigation | One `<nav slot="navigation">` of links with icons. Above 920 px it is a 14rem sidebar; below, `wa-page` moves it into a drawer opened by the menu button (`data-toggle-nav`). Links close the drawer (`data-drawer="close"`). The current view has `aria-current="page"` and the brand's quiet fill. Devices and Suggestions carry a warning `<wa-badge>` count |
| Selected room | At 75rem (1200 px) and wider, the room's details take the place of "The house now" beside the house model. Narrower, they open in a `<wa-drawer>`: from the end on a tablet, from the bottom under 40rem as a bottom sheet with the setpoint first |
| Main | At most 96rem wide, with `wa-page`'s own padding (16 px on a phone). On the House view the subheader's status line is hidden, as the hero says it |
| Cards | `<wa-card>`, header slot for the heading and its actions. Legacy views draw `.card` from the same panel tokens |
| Gaps | `wa-gap-*` utilities and `--wa-space-*` tokens. The House view's sections are `wa-gap-l` apart |
| Corners and borders | The theme's: `--wa-panel-border-radius` on cards, `--wa-form-control-border-radius` on controls, `--wa-border-radius-s` on bars and lanes |

## Motion

Web Awesome components bring their own transitions (drawer, details, dropdown, switch, button), and they respect `prefers-reduced-motion`. Radiate's own motion follows Emil Kowalski's design-engineering rules:

| Rule | How it is done |
|---|---|
| Animate `transform` and `opacity` only | Press feedback is `scale(0.97)` on menu links and the "Needs you" chips (`0.98` on a room in the phone list) |
| Strong ease-out for anything that moves | `--radiate-ease-out: cubic-bezier(0.23, 1, 0.32, 1)`, 160 ms for presses |
| Stay under 300 ms | Stale data fades to `opacity: 0.55` over 200 ms. Selecting a room swaps "The house now" for its details: the new card fades in and rises 6 px over 200 ms. A setpoint press moves the value 6 px the way it changed over 180 ms, like a dial. When the house changes state the hero's icon settles from `scale(0.85)` over 240 ms, and its colour cross-fades |
| Hover only for real pointers | Hover styles sit inside `@media (hover: hover) and (pointer: fine)` |
| Respect reduced motion | Under `prefers-reduced-motion: reduce`, presses stop scaling and only colour and opacity change |
| No animation on keyboard-driven changes | Keyboard actions apply instantly; a setpoint changed from the keyboard doesn't move |
| Transitions, not keyframes, for live data | Values change every tick; transitions retarget, keyframes restart |

The house model has the page's one keyframe animation: a room's radiator bar blinks while the room is calling or topping up, and always on the bypass room, as a hard on and off (`steps(2)`) every 1.8 s. It stops under reduced motion and the bar stays on. Opening "Week schedules" scrolls smoothly, or jumps under reduced motion. In the room editor nothing animates: a room follows the pointer or the arrow keys exactly.

## Accessibility

- The pages declare `lang="en-GB"` and `color-scheme: light dark`.
- Text meets WCAG 2.1 AA: 4.5:1 for body and small text, 3:1 for large text. The theme's `on` tokens are tuned for that on their fills; check both schemes when you add a colour of your own.
- Use Web Awesome's form controls for what they are: `<wa-radio-group>` for the heating and demand modes (a radiogroup with arrow-key movement), `<wa-switch>` for Boost hot water and Fire lit, `<wa-number-input>` for a setpoint, `<wa-input>` with a visible `label` for every text, date and time field. Where a native control needs ARIA a component can't forward (the alerts' "Show N more" with `aria-expanded`, the rooms list with `aria-pressed`), use a native `<button>`; Web Awesome's native styles draw it like its own.
- The focus ring is Web Awesome's (`--wa-focus-ring`, the brand colour, 3 px) on `:focus-visible`. Never remove it. In the house model a focused room draws its top in `--wa-color-focus`.
- The status line is `aria-live="polite"`, so screen readers hear the boiler state change without being interrupted.
- Moving to a view puts focus on its heading. Selecting a room on a wide screen puts focus on its name in the aside; closing the drawer returns focus to the room that opened it.
- Decorative graphics are `aria-hidden="true"`. Graphics that carry data, such as the burn timeline and each strip in today's plan, are `role="img"` with an `aria-label` in words.
- In the house model each room is a focusable `role="button"` with `aria-pressed` and a label such as "Lounge, 20.5 degrees, heating". Enter or Space selects it. In the room editor each room is a `role="button"` labelled with its name and size.
- The setpoint is a `<wa-number-input>` labelled "Setpoint, °C" with the room's name in its `aria-label`; its steppers move 0.5° and stop at 5° and 28°, and Up and Down do the same from the keyboard.
- Touch targets are at least 44 px on touch screens: Web Awesome's controls are, the menu links are 2.75rem under `(pointer: coarse)`, and a room in the phone list is at least 2.75rem tall.

Stale data is the one deliberate exception to the contrast rule: it dims to 55% opacity so it reads as out of date, and the status line above it keeps full contrast and says how old it is.

## Copy

UI text follows the same writing rules as the docs: UK English, metric units, no em or en dashes as punctuation, plain words.

- **Point first.** Say the state, then the detail: "Burner on for 12 min." then "Heating Lounge and Bedroom 3."
- **Say why the burner is on.** When no room is calling, the status line names the rooms the heat is going to and why: "Burner on for 290 min, topping up Bedroom 2 and Dining room to save a second burn soon." or "Burner on for 6 min to finish its minimum burn, with the heat going to Toilet." When the hot-water store is on, it ends with "Hot water on."
- **Room name first in reasons**: "Lounge: fire lit, radiator closed and learning paused". Reasons come from the core's `Reason.message`, so write them there with the UI in mind.
- **Plain words over internal terms.** "Opening valves" for the `lead` state, "Resting" for `rest`, "learning paused: hot water" for the `store_recovery` gate. Glossary terms appear where the reader needs them, such as "Opening limit" and "Supply factor".
- **Sentence case** for labels and buttons: "Boost hot water", "Fire lit".
- **Units every time**: `20.5°` for temperatures, `35%` for openings, `12 min` for durations, `K/h` for rates. Times are 24-hour local time (`07:10`).
- **Missing values** show a single placeholder glyph, `–`, never `0` or blank. This is the only place a dash character appears.
- **Errors say what happened and what Radiate is doing about it**: "Cannot reach Radiate. Retrying… Showing data from 14:32.".
- No exclamation marks, no blame, no marketing words.

## States to design for

Every view has to make sense in each of these states. When you add a component, decide what it shows in each one.

| State | What the reader must see | How it shows today |
|---|---|---|
| Loading | That the page is connecting | The hero reads "Connecting…"; the house model and Rooms show a spinner and "Waiting for the first reading from Radiate…" until the first state arrives |
| Offline | That the data is stale and Radiate is retrying | When the WebSocket drops, the page polls once per reconnect attempt (2 s, backing off to 15 s). If the poll fails too, the page dims, the hero turns warning with "Showing old data" and the status line says "Cannot reach Radiate. Retrying… Showing data from 14:32." With no state yet the hero says "Cannot reach Radiate". When a state arrives again the page brightens and a toast says "Connected to Radiate again." |
| Demo | That nothing is real | A compact `radiate-cool` callout at the top of every view with the simulated time and boiler, store and stairs temperatures, and in the online demo a line that nothing controls a real boiler and a Speed radio group (1×, 60×, 300×) |
| Dry run | That Radiate is not writing to devices | A compact warning callout at the top of every view: "Dry run. Radiate reads the house but doesn't switch the valves or the boiler.", the held-back valve writes and boiler commands, and the latest five writes behind a `<wa-details>` |
| Alerts | What needs attention, in words | Alerts about a room are "Needs you" chips in the hero, room name first, each opening that room; a problem three or more rooms share is one chip that leads to Devices ("TRV not reachable, 8 rooms"). The rest (a router, the boiler relay) are a compact warning callout under the hero, "Needs attention", one alert per item, two shown and the rest behind "Show N more" (a native button with `aria-expanded`), then "See devices" when any are device alerts, and "What these alerts mean". A server without `alert_details` lists every alert in the callout |
| Sign-in | That the server needs its token | When the API answers 401 and login is off, a `<wa-card>` "Sign in to Radiate" with a password `<wa-input>` replaces the views. The token is kept in `localStorage` and sent as a Bearer header and as the stream's first message. A refusal is a warning callout. Never shown through Home Assistant ingress or in the demo |
| Login | Who can sign in, and how | With login on (`GET auth/config`), a 401 sends the page to `login` instead of the token card. See the login page component. Never shown through Home Assistant ingress, to token users or in the demo |
| Signed in | Who is signed in, their role, and how to sign out | The account menu in the header (see its component), shown only for a login session |
| Role | What this person can't change, and why | A control the role can't use stays in place, disabled, with a neutral `<wa-tag size="s" class="lock-tag">` beside it: "Read only" for a viewer, "Ask an admin" for a household member. A viewer: the heating and demand modes (one tag under them), Boost hot water, a room's setpoint and Fire lit (tag under the setpoint, Resume schedule hidden), Set away (Back now hidden), the week view (no grips or Adjust, tag in the Schedules line). A household member: Arrange rooms, Set up your household and Change household setup, Scan network. The Settings link shows only for an admin. Disabled Web Awesome controls draw themselves as disabled; locked native buttons have `cursor: not-allowed`. The server refuses the same changes (403), so the tag is never the only check |
| Safe mode | That the boiler is stopping and why | Shown as an alert |
| Change on its way | That the press counted, and whether the server took it | A change to the heating mode, demand mode, Boost hot water or Fire lit shows at once (`web/src/pending.js`), with `aria-busy` and the control at 0.75 opacity while the request is out; a setpoint shows its new value the same way, with "Sending…" as its hint. Straight after the server answers, the page fetches the state, so the change doesn't wait for the next tick. A state from before the press can't undo it: the press holds until a state agrees, or 5 s after the server took it. A refused change goes back to the server's value with a line in amber under the control (`role="alert"`): "Not saved: ask an admin." for a role refusal, "Not saved: your sign-in has expired. Reload the page." for a stale session, otherwise "Not saved. Try again." Back now and Save show a spinner while they send. Once the server takes a change, a toast at the bottom of the screen says what happened (\"Lounge held at 21.0°.\", \"Heating: Frost protection only.\", \"Hot water on for 60 minutes.\", \"Sam is home.\"); a refusal is never only a toast |
| Boiler states | Idle, opening valves, firing, resting, with minimum burn and minimum off progress, and why the burner is on | A `<wa-badge>` beside the Boiler heading (Idle neutral, Opening valves warning, Firing brand, Resting cool), the status line, and while firing or resting a `<wa-progress-bar>` of the minimum burn or minimum off with its countdown under it. The bar and countdown use the effective minimum off from `state` |
| Boiler not linked | That Radiate can't switch the boiler, so it never claims the boiler is idle | When `telemetry.boiler_linked` is false (no `shelly` section), the status line reads "No room needs heat. The boiler switch isn't linked yet." or "Lounge and Toilet want heat. The boiler switch isn't linked yet, so the boiler follows its own timer." The Boiler tile on the house now card reads "Not linked" with "Radiate can't switch it until the relay is set up." Servers that don't send `boiler_linked`, and the demo, keep the usual wording |
| Boiler relay unreachable | That Radiate can't see or switch the boiler right now, so the burner figures can't be trusted | When `alert_details` has `driver.shelly`, the status line reads "Radiate can't reach the boiler relay, so it can't see or switch the boiler. If its watchdog is installed, the Shelly runs the heating on its own schedule until Radiate reconnects." The boiler badge reads "Not reachable" (warning), the Boiler tile on the house now card reads "Not reachable" with "Radiate can't see or switch the boiler right now.", and Burner today reads "Not counted while the relay can't be reached". The demo never shows it |
| House layout | Whether the model shows the owner's layout or a guess | Until a layout is saved, a muted hint under the model heading: "Rooms are placed by a guess from their names. Arrange them to match your house." A server without `GET layout` keeps the guess, and the editor says "This server can't keep a layout. Update Radiate to save it." A refused save reads "Not saved: …" with the server's message; a failed one, "Not saved. Check the connection and move a room to try again." |
| Short-cycling | That minimum off has been raised and for how long | A small warning callout on the Boiler card, "Short-cycling." then "Minimum off raised to 15 min for the next 23 h 30 min, so the burner starts less often." Hidden when `boiler.short_cycle` is absent or null |
| Daily accounting | Burner time and starts today, how well balanced yesterday was | "Burner today" (hours, starts, and litres and kWh when a nozzle rating is set) and "Balance, yesterday" (score out of 100, and "Last room 22 min after the first" for the median arrival spread) in the statistics. "No full day yet" until a day has closed. Servers without `accounting` show the old "Burner hours" total |
| Demand mode | Which mode is in effect, what it does, and whether it is the configured default | Demand, a radio group of Eco and Comfort beside Heating, with its hint under it: "Default: fewer, longer burns. Rooms might warm a bit later." or "Every room held at its target, with more burns." A failed change reads "Not saved. Try again." in the hint, in warning colour. Hidden when the server sends no `settings` |
| Room states | Heating, preheating, waiting for a burn, topping up, heat sink, fire lit, comfortable, waiting, bypass, no radiator | A badge in the rooms list and the room's details. "Waiting for a burn" (warning) is a room calling in eco while it waits for other rooms (`reason_code` `demand.pooled`); its reason reads "Waiting to share a burn with other rooms." and, with the boiler idle, the status line names it: "Boiler idle. Toilet is waiting to share a burn with other rooms." "Topping up" (brand) is a burn extension, which keeps the burner on; "Heat sink" (cool) is a room opened only so the heat has somewhere to go. Each has a one-line reason in the room's details. A server without `extend` shows "Topped up" |
| Setpoint held | That the schedule is overridden, until when, and how to undo it | A cool "Held" tag beside the room's badge, a hand icon before its setpoint in the rooms list, and the setpoint panel in cool with its hint: "Held until 22:30", "Held for 1 h 20 min" or "Held until cleared", with a "Resume schedule" button. A failed change reads "Not saved. Try again." in warning colour in place of the hint |
| Away | Who Radiate counts as away, until when, and how to change it | People section, shown only with a household. A `<wa-card>` per person with a badge: "Home" or "Out" (neutral), "Away" (cool), "Due back" (warning, while their rooms warm up), "No update" (warning, presence gone stale). A line in words: "Away until Tuesday 18:00.", "Away since 09:10, from Home Assistant.", "Out since 14:05. Counts as away after 1 h.", "Due back at 18:00. Warming up their rooms.", "Home Assistant hasn't reported for over 1 h, so Radiate treats them as home." "Set away" opens a date and an optional time; "Back now" clears it. While everyone being away holds frost, a cool callout says so above the people. Within the return warm-up, a cool callout says "Warming up for Early riser's return at 18:00." (or "tomorrow at 18:00") |
| Household setup | Whether a household is set up, how to start or change it, and where it is saved | Without a household, a card above the controls: "Set up your household", a sentence on what it does and a primary button. With one, a "Change household setup" button beside the People heading. Neither shows on a server without the setup. The wizard replaces the dashboard until it is closed or saved; a cool note at the top says where the answers come from and, for a saved setup, offers "Use the house file's setup instead" with an inline confirmation. After saving, a cool callout at the top of the House view says so for 15 s |
| Schedules | The week each room follows, why it changed and anything left out | The Schedules view (`#schedules`), under People, one card per controllable room. Hidden on a server without `GET /api/v1/schedules` or with no rooms to show. With a household the server lets the web UI change, household rooms can be adjusted (see the week card): a moved edge waits in a cool panel with the change in words ("Mon to Fri: warm until 23:00, not 22:30."), the week as it would be, any new dropped-period note, and Save and Cancel. Kitchen follows its new week." A failed save reads "Not saved. Check the connection and try again." in amber |
| Stuck valve | That a radiator stays cold when it should heat | A small warning callout in the room's details: "Valve may be stuck: radiator stayed cold for 3 burns." Also in the alerts |
| Learning paused | Why the room is not learning | A line in the room's details, for example "Learning paused: window" |

## Components

**App shell.** `<wa-page>` (see Layout and shape). The header holds the menu button on a phone, the brand (the `fire-flame-curved` icon in the brand colour and "Radiate"), the outdoor temperature ("Outside 7.1°") and, for a login session, the account menu. The subheader holds the status line. The navigation lists House, Devices, Suggestions, Savings, Settings, Raw data and Guide, each with its icon; a view's link shows only once the server offers it, and House and Guide always show. Above the views sit the notes that apply to every view: the demo banner, the dry run notice, the learning notes and the sign-in card.

**House view.** It answers three questions in order: is the house all right, what is the boiler doing and why, and which room needs you. In order: the hero, the alerts and guide notes, the house model with "The house now" or the selected room beside it (stacked under 75rem), Rooms, then the Boiler card beside today's plan and the savings line. About one and a half desktop screens. People and the weekly schedules are on the Schedules view.

**Hero.** The first card on the House view. An icon in a quiet tone fill (success when the house is comfortable, brand while heating or opening valves, warning when the relay can't be reached, in safe mode or showing old data, cool for frost or quiet hours, neutral when off or waiting), a title ("Rooms are comfortable", "Heating 2 rooms", "2 rooms want heat", "Burner resting", "Quiet hours until 06:00", "Frost protection only", "Heating is off", "The boiler relay can't be reached", "Safe mode: the boiler is stopping", "Showing old data"), the status line (why) read out when it changes, and facts: outside temperature, hot water and the next setpoint change. Under a rule, the controls: Heating (Auto, Frost, Off) and Demand (Eco, Comfort) as `<wa-radio-group>`s of button radios, and Boost hot water as a `<wa-switch>` with the hint "On for 60 minutes." Demand's hint says what the mode does; it starts "Default:" while the server follows the configuration file, and that prefix is the only sign of the default. Picking the configured default sends `null`. Under another rule, "Needs you" chips (see Alerts). On a phone the radio groups take the full width.

**House model.** The "Your house" card (`web/src/house.js`), with a 12° to 22° key and an outlined "Arrange rooms" button in its header, a help line, then the model. It draws the house as an axonometric model: each floor's rooms as blocks, floors stacked and pulled apart so an upper floor never hides the one below, each floor tagged with its name. A block's top is the room's temperature colour and its two sides are darker shades of it. The reading sits on the top, with the name under it when the room is at least 1.4 m wide. A room with no reading is `--hm-none` and reads `–`. A radiator bar runs along the front edge while the room is calling or topping up, and always on the bypass room (see Motion). Selecting a room selects it everywhere (see Rooms) and outlines its top in `--wa-color-text-normal`. The model is redrawn on each state, when the colour scheme changes and once the fonts load. The layout only draws the model; control never reads it.

**Arrange rooms.** The model card becomes a floor-plan editor, headed "Arrange rooms", with "Start again" and a brand "Done". Under the heading: one native button per floor (the selected one brand, the others outlined, `aria-pressed`), "Add floor" up to six floors, a "Floor name" `<wa-input>` (up to 40 characters), and "Remove this floor" when a floor has no rooms and isn't the only one. The plan is a 14 by 10 m well in `--wa-color-neutral-fill-quiet` with a gridline every half metre and a stronger one every metre. Rooms are blocks in their temperature colour, with the name at the top and the size ("4 × 3.5 m") at the bottom. Dragging a room moves it, and dragging the 14 px square in its corner resizes it, using pointer events with `touch-action: none` on the plan. Everything snaps to 0.5 m and a side is at least 1 m. With the keyboard, Enter or Space selects a room, arrow keys move it half a metre, and Shift with an arrow resizes it. Under the plan, rooms not placed yet are dashed outlined buttons ("Place Kitchen"), or "Every room is placed.", and "Take Kitchen off the plan" for the selected room. A placed room goes in the first free 2 by 2 m spot on the floor. "Start again" puts every room back where the guess from their names puts them. Each change is saved with `PUT layout` 500 ms after the last one, and a quiet line says "Saving…", then "Saved." or why not. While the editor is open, the house now card becomes "Live model": the model as it will look, with "2 floors, 8 of 9 rooms placed." and a sentence saying the layout only draws the house. "Done" closes the editor and returns focus to "Arrange rooms".

**Guessed layout.** Until the owner saves a layout, rooms whose names suggest an upper floor (bedroom, bathroom, landing, en suite, nursery, study, loft, attic) go on "First floor" and the rest on "Ground floor", three to a row at 3 by 3 m. If every room matches, or none does, there is one floor.

**The house now.** The card beside the model, until a room is selected. A big readout of rooms calling over controllable rooms ("3/8"), which the sentence beside it continues: "rooms want heat.", "rooms are heating. Burner on.", or, without a boiler relay, "rooms want heat. The boiler switch isn't linked yet, so the boiler follows its own timer." With no room calling it reads "No room needs heat right now.", and with the heating off or on frost, "Heating is off." or "Frost protection only." "Where every room sits" puts every room with a reading as a tick in its temperature colour on a 12° to 22° axis, with a line at the target most heated rooms aim for, and says the coldest and warmest rooms in words under it. Then four tiles in a 2 by 2 grid, each an icon, a label, a value and a note on a quiet fill: Boiler (its state, with minutes so far while firing or starts in the last hour otherwise, "Not linked" or "Not reachable"; brand while firing, warning when not reachable); Dry run with the count of held-back writes (warning), or Mode with the demand mode when not in dry run; Devices needing attention (warning when any do); Learning, the average model confidence of the controllable rooms. Last, "Coming up": the next three times a setpoint changes, rooms at the same time on one line ("07:00 Bedroom 1 and Bedroom 2 warm to 19.0°."). Without any setpoint changes ahead, "Coming up" is left out.

**Rooms.** A `<wa-card>` headed "Rooms" with a help line. On a wide screen, a table inside a `<wa-scroller>`: the room (a swatch in its temperature colour, its name as a button with `aria-pressed`, cut with an ellipsis past 16rem, and a warning icon when it needs you), Now, Setpoint (a hand icon labelled "Held" while held), Opening limit (a small `<wa-progress-bar>` and the percentage, faded to 0.45 while the room isn't taking heat) and State (the badge). The selected row has the brand's quiet fill. Under 40rem it is a list of buttons, each the swatch, name and badge over "Now 20.5°", "Set to 19.0°" or "Held at 21.0°", and "Valve 35%". Selecting a room shows its details: beside the model at 75rem and wider (focus moves to its name; Escape or the close button closes them and returns focus), otherwise in a `<wa-drawer>` labelled with the room's name that closes on a tap outside. Selecting the room again on a wide screen clears it. A missing reading or opening is `–`.

**Room details.** The name, badge, a cool "Held" tag and a close button; the reason line; Now, Target and Opening limit as readouts with the opening limit as a `<wa-progress-bar>`; a warning callout for each problem with the room's devices, and for a stuck valve; the setpoint (first, under the name, in the phone's bottom sheet); Fire lit for rooms with an open fire; humidity, the setpoint of a room Radiate doesn't control, and Learning ("Learning now", "Paused: window"); and "What Radiate has learned" for a room with a model.

**Setpoint.** A quiet panel (cool while held) with "Setpoint" and its hint on the left and a stepper on the right: an outlined minus button, the value, an outlined plus button. Each button's icon names the room ("Lower Lounge setpoint by 0.5°", "Raise Lounge setpoint by 0.5°"); the group is labelled "Lounge setpoint" and the value is an `<output>` read out when it changes. Steps of 0.5 °C from 5 to 28 °C; a button is disabled at either end. Presses change the value at once and are sent together 600 ms after the last one, so several quick presses make one request, then a toast says "Lounge held at 21.0°." The page asks for the state straight away, as the server only streams once a tick, and the value stays as set until a state confirms it, or for 5 s. A hold ends at the next scheduled change by default.

**Fire lit.** A `<wa-switch>` with the hint "Radiate closes this radiator and pauses learning while the fire warms the room." It shows the switch a person set (`fire_switch`), not a detected fire it can't clear.

**What Radiate has learned.** A `<wa-details>` at the foot of a room's details, closed by default, with a cool "Still learning" tag in its summary while the heating gain's confidence is under 0.4 or nothing is learned. The body: a "Still learning." line in cool when the tag shows, then label-over-sentence rows written by `web/src/learned.js` from `rooms[].model`: Warms up, Cools down, Other heat, Heat arrives, How sure, Used for, Relearned and Started again (the wording is in `learned.js` and tested in `tests/server/test_learned_js.py`). Under the rows, the model's own numbers in small quiet text ("In the model's own terms: heating gain 3.81 K/h, …") and a link, "What the room model is". It has no controls, so every role sees the same. No chart: the sentences carry the numbers.

**Boiler card.** A `<wa-card>` headed "Boiler" with the state badge. While firing or resting, the minimum burn or minimum off as a `<wa-progress-bar>` (cool while resting) and its countdown; the short-cycling callout; the last 24 hours as two lanes, burns in the brand colour and hot water in cool, with hour ticks and a key; and the statistics. Boost hot water is in the hero.

**Boiler statistics.** Burner today, starts in the last hour, predicted burn, yesterday's balance score and the supply factor, in a grid of label over value. Secondary detail sits under a value in small quiet text. Every value is optional: a missing key or a null shows `–`.

**People.** On the Schedules view, a section headed "People" with "Change household setup" beside it, the away callouts, then a `<wa-card>` per person: the name and badge in the header, one line of state, then "Set away" (or "Change") and "Back now" while an away until is set or Home Assistant says they're out. "Set away" opens a form in place, with no animation: "Away until" and "Back at" (`<wa-input type="date">` and `type="time"`, the second optional), a line that without a time they count as back from the start of that day, Save and Cancel; a toast confirms ("Sam is away until Tuesday 18:00.", "Sam is home."). The date takes focus; Escape or Cancel closes the form and returns focus to "Set away". Days read "today", "tomorrow", a weekday within the week, or "Tue 2 Dec"; a time of 00:00 is left out. Times are house time, taken from the server's local ISO strings.

**Savings line.** On the House view, under today's plan, once savings have figures: a piggy-bank icon and the headline sentence as a link to `#savings`. Hidden while learning or unavailable.

**Help lines.** One quiet sentence (`.help-line`, `--wa-font-size-s`) and at most one link into the Guide, where people get stuck: the house model, the house now ("The big number is rooms that want heat, out of the rooms Radiate controls."), today's plan, Rooms ("Select a room to change its temperature until its next scheduled change."), the Schedules line, the Devices head, the Suggestions line, the Savings head and Needs attention ("What these alerts mean"). Link text names the topic ("How to read the model", "What battery, signal and offline mean"), never "Learn more" or an appended arrow. Links are Web Awesome's native links. Help lines are made once and never redrawn with the live data, so focus on a link survives each tick; that is why the house now card and today's plan redraw only their figures (`.hm-live`, `.hm-tl`). No tooltips or popovers.

**Today's plan.** A `<wa-card>` beside the Boiler card, hidden until `GET schedules` has answered, with a "Week schedules" button in its header that opens the Schedules view. One row per scheduled room: the name, then today as a 1rem strip of its setpoints in temperature colours, with a now line haloed in the surface colour. Hour ticks at 00, 06, 12, 18 and 24. Each strip is `role="img"`, labelled with the day in words.

## The other views

Devices, Suggestions, Savings, Settings with the security log, Raw data, the week schedules, the household setup and the Guide are drawn by their own modules (`web/src/devices.js` and so on) and laid out in `web/src/styles/views.css`, `savings.css`, `settings.css`, `data.css` and `guide.css`. Plates are `<wa-card>`s, badges `<wa-badge>`s painted from a state word (`paint()` in each module: success, warning, neutral or `radiate-cool`), notes `<wa-callout>`s, segmented choices `<wa-radio-group>`s of button radios, "Show as table" a `<wa-switch>`, meters `<wa-progress-bar>`s and buttons `<wa-button>`s, apart from the native ones described at the top of this page. Each view opens with an `h1` and a one-line summary. Where the text below names an older token (`--cool`, `--warn`, `--heat`, `--line`, `--surface-2`), read Radiate's cool, warning, brand, the surface border and the neutral quiet fill.

**Week card.** Name and a neutral badge, "Household" or "Hand-written"; the away line and usual week when they apply; seven day rows (Mon to Sun) of a 24-hour bar; hour ticks at 00:00, 06:00, 12:00, 18:00 and 24:00; the week in words, one line per run of identical days; dropped-period lines; "Depends on …" with the room's people. A warm period is a block with a `--heat` edge and a `--heat` fill whose opacity follows the temperature (0.3 to 1 across the coolest and warmest setpoint shown, widened to the household levels), so 19° looks the same in every room. Its temperature is written above it in `--ember`; labels never overlap, and one that cannot fit is left to the day's words. Each bar is `role="img"` labelled with the day in words, and today's row has `aria-current="date"`, a bold day name and a `--text` now marker with a `--surface` halo. Faint `--line` gridlines every 3 hours. A legend lists the household levels with their temperatures, and "Adjusted" when a room has adjustments. The bar compresses on a phone. The pure helpers in `web/src/week.js` take minutes of the day, so the wizard's Result step reuses them; there the bars are read-only.

**Adjusting a week.** In the Schedules section, a household room's warm periods have a grip at each edge: a 6 px `--surface` bar with a `--heat` outline, `cursor: ew-resize`. With a mouse the grips fade in (opacity, 150 ms) while the pointer is over the card; on touch screens they are always shown. The hit area is 24 px wide, and 44 by 50 px under `(pointer: coarse)`. A run of identical days moves together, so dragging Wednesday's evening end moves Monday to Friday, and the change applies to those days. Dragging uses pointer events with pointer capture, one pointer at a time, `touch-action: none` on the grip only, and snaps to 15 minutes. While an edge moves, its time is written above it in bold `--text` and the day's temperature labels hide. Nothing animates: the block follows the pointer or key exactly. A later end or an earlier start keeps the room warm, the other way keeps it cold; an edge can't cross the other edge of its period, less 15 minutes, or a neighbouring period. On release the change is previewed (`POST household/preview`) and waits for Save. Keyboard: only the first day of each run is a tab stop. Each grip is `role="slider"` named "Bedroom 1, Mon to Fri, warm until 22:30", with the time as `aria-valuetext`. Arrow keys move it 15 minutes, Page Up and Page Down an hour, Home and End to its limits; the preview waits until the keys stop for 400 ms. Enter saves, Escape cancels and puts every edge back. After a save, focus returns to the same grip, or to "Adjust" after a pointer save. Adjusted time has a 3 px `--cool` line along the bottom of the bar. Under the week, a room with adjustments lists them in words ("Kept warm 22:30 to 23:00 on weekdays.") with a "Remove" link each, its week without them ("Without adjustments: …"), and "Reset to routine". "Adjust" opens a form in place with no animation: Days (every day, weekdays, weekend or a day), "Keep it" warm or cold, From and To as 24-hour text inputs. Escape or Cancel closes it and returns focus to "Adjust". An error appears under the fields in amber, and the field it is about gets `aria-invalid`. A room that someone being away has changed has no grips, as its week isn't its usual one, but keeps its list and the form.

**Setup wizard.** A heading with "Close", the five steps as a list (the current one bold with a `--cool` underline, visited ones as links), then one card per step: a heading, a one-line introduction, the questions, an "Advanced: …" disclosure, and Back, "Step 2 of 5: Routines, Sam" and Next along the bottom. Next reads "See the result" on Temperatures and "Save" on the Result. Questions are plain and name the person: "When does Sam get up?", "Is Sam out or working from home during the day?", "Where does Sam work?", "When does Sam go to bed?", "How is it used?", "What kind of room?", "Who uses it?". Every answer starts filled in, so Next always works on a first visit. On People, each person is a `role="group"` row with their name, "Home Assistant person" and Remove. "Home Assistant person" is a choice of "Not linked" and the people Home Assistant reported, by name (with the entity ID when two share a name), or, when Home Assistant hasn't reported any, a text input for the entity ID. One muted line under the list says what linking does, and every link's `aria-describedby` points to it. Each Advanced setting has a one-line explanation ending with its default ("Default 1 h."); per-person and per-room settings are empty, with the house's value as the placeholder. Room kinds are explained in a sentence under the choice. Below 12° an amber line under the unused or night temperature gives the damp note. Errors are amber, at the top of the step and under the answer. The Result is the week card for every room, with any advice and a sentence on warm periods left out of the valves' own schedules.

**Device card.** Name ("Lounge TRV", "Bathroom room sensor", "Router plug_hall", "Boiler relay"; a room whose name ends in " room" doesn't repeat it, so "Dining room sensor") and a status badge: "Online" (`--ok`), "Needs attention" or "Offline" (amber), "No data yet" (neutral). Problem lines, then three values: Battery (the percentage and a 26 by 6 px meter scaled with `transform`, `--ok` or `--warn` when low; "Mains" for mains devices), Signal (three bars, `--ok` strong, `--muted` fair, `--warn` weak, the word, and "LQI 101" in muted 0.72rem under it; "Wi-Fi" for the relay) and Last seen ("just now", "4 min ago", "3 h ago"). Then the latest readings in one muted line ("18.1° at the valve, opening limit 35%, heating, auto mode", "20.4°, 56% humidity", "Heating on, hot water off"), and a meta line with the Zigbee2MQTT name in `code`, model, firmware and route ("Via plug_hall (LQI 93)", "Via the coordinator"). Cards sit in a `repeat(auto-fill, minmax(260px, 1fr))` grid under "Valves and sensors", "Zigbee network" (the scan card, the route tree and the routers) and "Boiler". The route tree is nested lists from the coordinator, each line a device with its link LQI, amber when weak. Cards are created once and updated in place; the meter is the only thing that moves.

**Suggestion card.** Title, point first and naming the room ("Bedroom 2 loses heat quickly", "Bedroom 3's radiator may be too small"), and a badge: "Act on this" (amber), "Worth considering" or "For information" (neutral). A card to act on also has a 3 px `--warn` left border, so the most pressing stand out without colour alone. Then the evidence in words, with the numbers and units ("cools by about 1.7° an hour. That is 3.3 times the house's typical 0.5° an hour."), a muted "What to do" label over the action, and a muted line with the confidence and what it rests on ("Medium confidence. From 87 h of learning in Bedroom 2."). Words that hedge ("may", "about", "Radiate's model says") are deliberate: a suggestion is never presented as fact. Cards sit in a `repeat(auto-fill, minmax(min(100%, 340px), 1fr))` grid, are created once and updated in place, and nothing on them moves.

**Savings chart.** Inline SVG drawn by `web/src/savings.js`, no chart library, redrawn only when the body or the width changes (a `ResizeObserver`), at 220px tall, 180px under 520px. One slot per day, or per week with the Days and Weeks segmented control (shown from 8 days). Oil used is a solid `--heat` bar; the baseline's litres a wider 1.5px `--text` outline drawn around it, so the gap above the bar is the saving and a day that used more shows its bar above the outline: outline against fill, never colour alone. A day not counted is a full-height slot hatched in `--line`, never a zero. The y axis starts at zero with a 1.5px ink zero line, `--line` gridlines at a round step (about four), and the top tick carries "L"; ticks and date labels are Funnel Display 700, 11px, tabular. The chart is a `role="group"` labelled with its trend ("Bar chart of oil used each day against the baseline, 24 days from 2 Nov to 25 Nov. Less than the baseline on 18, more on 5. 1 not counted."). Each slot is a `role="img"` with its words as `aria-label`; one slot is a tab stop and the arrow keys, Home and End move between them, with a 2px `--cool` ring on `:focus-visible`. The chosen slot's words sit in a line under the chart (`.sv-readout`), so they read the same with a mouse (hover), the keyboard and touch (tap), and it defaults to the latest day. A legend of swatches names "Oil used", "Baseline, estimated" and "Not counted". "Show as table" (`aria-pressed`) shows the same numbers, one row per day, in a table that scrolls inside its own box on a phone. Nothing in the chart animates, and numbers never count up.

**Savings side plates.** Beside the chart above 1100px, under it below. "Saved so far": a 90px line of the running total in ink against a zero line, and a sentence with the total. "Estimated share, last 30 days": one row per room, sorted, a 10px `--surface-2` track with an ink bar scaled with `transform` from zero, right for a saving and left of a centre ink line for oil over the baseline, the litres with a real minus sign, and the room's warm share and shortfall in muted 0.78rem text.

**Raw data view.** `#data`, the "Raw data" link between Settings and Guide, shown when `GET data/series` answers with a history (`web/src/data.js`, `web/src/styles/data.css`). Moving to the view focuses its heading. The head says what is recorded ("65 series from Mon 16 Nov 05:00 to now. Kept for 14 days.") and has one help line linking to the Guide's "Raw data and exporting it". Above 1100 px a 360 px column holds "Find a reading" and the export plate, with the chart plate beside them; below that they stack: controls, chart, export. "Find a reading" has a search field whose matches are a list of plain buttons under it (Enter picks the first, Escape clears), then Reading and Room selects (Room is "Whole house" and disabled for a house reading), a Time segmented control (6 h, 24 h, 7 days, 30 days), From and To `datetime-local` fields in house time (editing one makes the range custom), "One point every", a muted line saying what the answer covers, and Download CSV and Download JSON. The chart plate: the series as its heading ("Lounge temperature", "Temperature, every room"), "Show as table", statistics in the readout face (Latest, Lowest, Highest, Average; Latest and the share of time On for a state), then the chart: inline SVG, 260 px tall, 200 px under 520 px, redrawn only when the answer or the width changes. One series is in 2px ink; with several, the rest are 1.25px `--muted` at 0.45 opacity, and a legend of `aria-pressed` buttons with a line swatch picks which is in ink, so colour never tells them apart, and a muted line says whose figures the statistics are. Over a step wider than a minute, the ink series' lowest to highest in each step is a `--surface-2` band. States and levels draw as steps; their axis reads Off and On, or 0% to 100% when aggregated, or the level names. A 1.5px ink baseline, `--line` gridlines, ticks in Funnel Display 700 at 11px. The chart is one tab stop: arrow keys, Page Up and Page Down, Home and End move a cobalt cursor with a dot, and the words for that point sit in a line under it (`aria-live`), for pointer and touch too. The table shows the newest 500 points in a box at most 480 px tall with a sticky header. The export plate: "OpenTelemetry export" with a badge, "Sending" (`--ok`), "Waiting" (cool), "Failing" (amber, and a 4px `--warn` left rule on the plate) or "Not set up" or "Off" (neutral), one line point first ("Last sent at 09:28, just now.", "Can't send: HTTP 401: ... Trying again in 4 min, and keeping the data until then."), then where it sends, what is waiting, what was sent, and in amber what was dropped or rejected. Indexing, refusals and load errors are a flat band under the head with a 4px rule, cool or amber. Nothing animates beyond the shared press feedback.

**Learning list.** One row per controllable room in a card: the name, a 48 by 6 px `--cool` meter of hours learned against the hours needed (scaled with `transform`, only while learning), a badge "Ready" (`--ok`), "Learning" or "Not judged" (neutral), and the note in muted 0.84rem text.

**Settings view.** `#settings`, drawn by `web/src/settings.js` from the server's registry, so a new setting needs no UI code. The Guide's layout: a contents plate (two columns under 980 px) and one column of at most 52rem. Each section is an `h3.section-h` with a help line and one guide link, then a plate of rows. A row is the label, its source as a chip ("House file" and "Default" neutral, "Set here" `--cool` on `--cool-soft`, with a 3 px `--cool` inset rule down the row), an amber "Restart to use" tag while waiting, the help with its range, default and "Used after a restart." where that applies, and the control on the right (stacked under 640 px). Numbers are text inputs with the unit after them; on/off is a segmented control, with "Not set" for optional ones; choices are selects in words ("Valve's own sensor", "Open fire"); a room's use is two selects, Weekdays and Weekend; passwords are password inputs that are never filled ("Set. Type to replace it"). A row set here ends with "House file: 8 min." and a link, "Use the house file's, 8 min" or "Use the default, 7°". Each section, and each room, is its own form: "Save changes" appears only once something changed, with "Cancel changes"; "Use the house file for this section" shows when anything in it is set here. Rooms are `details` plates, closed by default, with "2 set here" and "Restart to use" badges in the summary. A change that can write to the boiler or valves opens a flat band in place with a 4px `--warn` left rule: "This lets Radiate write to the boiler or the valves: Dry run, Off. Check the wiring and the valves before you go on." with "Save and allow it" (focused) and "Cancel". The household and schedules sections have one button each: "Open the household setup" and "Show the schedules". "Use the house file for every setting" asks in place before it goes. Nothing animates except the room disclosure's chevron.

**Guide view.** `#guide`, static text in `web/index.html`, moved to by `web/src/guide.js`. A "Guide" heading and one line, then a contents card (250 px, sticky above 980 px, in columns above the text below that) and one reading column of at most 40rem. Each section answers one question, in docs register: What the colours mean, Read the house model, What the house is doing, Read a room, Make a room warmer for a while, Change the weekly times, Hot water, Heating modes, Eco and Comfort, When someone is away, Open fires and range cookers, What the room model is, What learning is, Why a room isn't heating, Devices, Suggestions, Savings, Settings, The security log, Raw data and exporting it, Alerts, When something goes wrong, Home Assistant. A section is a `section` with an `h3.section-h` (`tabindex="-1"`, `scroll-margin-top: 8rem`). Terms are a `dl` (`.g-terms`) of the badge or word exactly as the app shows it, as the same `<wa-badge>`, beside its meaning; under 560 px the meaning drops under the term. Pictures (`.g-fig`, `aria-hidden` and `inert`, so nothing in them takes focus) reuse what they explain: the temperature scale as a gradient of the `--t*` tokens, a model block at 19° with its blinking radiator bar (`.hm-rad`), the opening limit `<wa-progress-bar>` and a held setpoint `<wa-number-input>`. Only behaviour the code has goes in, and what the app can't do is said plainly (hand-written weeks and hot-water windows live in the house file; this page's holds always end at the next change).

**Guide routing.** The view is the part of the hash before a slash and the rest names a section, so `#guide/hot-water` shows the guide, scrolls to `#g-hot-water` and focuses its heading. Section elements are `g-<name>`, never the fragment itself, so the browser's own jump to a matching ID never fights the router (an earlier `#week` link broke that way). Opening the page on a view other than the house starts at the top. A second press on a link to the hash already showing routes again. The back button returns to where the reader was.

**Login page.** `web/login.html` and `web/src/login.js`, on Web Awesome like the House view. A column at most 28rem wide: the brand, then a `<wa-card>` headed "Sign in" with one quiet line, "Sign in to see the house and change the heating." Then whichever of these the server offers: a password form (Username and Password `<wa-input>`s with visible labels, the password with a show button, and a brand "Sign in" `<wa-button>`), a `<wa-divider>`, and one `<wa-button>` per single sign-on method with the configured label (outlined beside the password form, brand when it is the only way in). Before anyone has an account, the form is replaced by a cool callout: "No one can sign in yet.", the `radiate users add` command, and why the page never creates the first account. Errors are a warning callout (`role="alert"`): "That username and password weren't accepted. Check them and try again.", "Too many attempts for this account. Try again in 14 min.", "Single sign-on didn't work. Try again, or ask whoever runs Radiate to check its log.", "Cannot reach Radiate. Check the connection and try again." An empty or refused field gets `aria-invalid` and a warning border. Under the card, a quiet line says who can reset a forgotten password. The username field takes focus.

**Account menu.** The last control in the header, shown only for a login session: a `<wa-dropdown>` whose trigger is a small outlined button with a user icon and the username (clipped at 16 characters). It opens under the button, right-aligned: "Signed in as alex with a password." (or "with single sign-on"), a quiet role line ("Admin: you can change anything here.", "Household: you can change temperatures, away, fires, boosts and room adjustments. Settings and the household setup need an admin." or "Read only: you can see the house but not change it."), a divider and a "Sign out" item. The dropdown handles focus, Escape and a press outside. A failed sign-out says "Not signed out. Check the connection and try again." in warning colour under the status line.

## Phone width

- Design for 360 px wide first. The page never scrolls sideways.
- Below 920 px `wa-page` switches to its mobile view: the navigation moves into a drawer opened by the menu button, and the header holds the menu button, the brand and the outdoor temperature.
- Under 75rem the house model and the house now stack, and a selected room opens in a drawer. Under 40rem the Heating and Demand groups take the full width, Rooms becomes a list of buttons, and the drawer is a bottom sheet with the setpoint first.
- Under 32rem the names in today's plan narrow to 5.25rem and the rooms-calling readout sits above its sentence.
- The People cards and the week cards drop to one column; long names and reasons wrap and never push the layout wider.
- In the legacy views: suggestion and device cards drop to one column; the savings chart fills its card and its table scrolls inside its own box; the Guide's contents sit above the text below 980 px, in as many 240 px columns as fit, and the Settings contents use 150 px columns; Settings rows stack their control under the help below 640 px; the setup wizard is at most 820 px wide and under 560 px the step line moves above Back and Next.
- Touch targets are at least 44 px on touch screens (see Accessibility).

The online demo can't show every state. Under `npm run dev`, add `?fixture=<name>` (`web/src/dev-fixtures.js`): `relay-lost`, `safe-mode`, `dry-run`, `quiet`, `frost`, `not-linked`, `viewer`, `offline` and `worst` (fifteen rooms with long names and missing readings).
